# QC Review — Full-Codebase Audit — 2026-08-08

Scope: entire /root/availai production codebase. Domain reviewers reported findings; every
critical/high claim below was adversarially re-verified against source (and in two cases by
executing the real code). Mediums are reviewer reports, NOT independently verified.

---

## 1. Executive summary

The core CRM/sourcing logic is broadly sound, but the platform has one systemic defect class
and a cluster of money-path integrity gaps. The systemic problem: `app/utils/graph_client.py`
returns `{"error": ...}` dicts instead of raising on 401/4xx/exhausted retries
(graph_client.py:278, 304, 318), and at least seven send/lookup paths never check the return —
so failed emails (including prepayment OK-TO-WIRE / DO-NOT-WIRE notices, approval decisions,
vendor replies, and customer-facing proactive offers) are recorded as delivered. Separately:
deleting a reopened quote CASCADE-destroys its buy plan, quality plan, and PAID prepayment
rows; the quote-number generator is deterministically wedged by any revise of a non-latest
quote; approval authority can be reassigned past the eligibility/amount-limit system; two XSS
vectors exist; and both deploy safety nets (the release CI gate and the rollback path) are
broken-on-use. Counts: 32 confirmed critical/high reports = 31 unique defects (3 critical,
28 high), presented below as 27 entries after dedup; 58 medium reports = 54 distinct issues;
0 claims refuted.

## 2. Confirmed findings (adversarially verified), ranked

### CRITICAL

**1. Quote numbering wedges all quote creation after any revise of a non-latest quote**
- Where: app/services/crm_service.py:39-53 (reported independently at :48 and :42 — deduped)
- What breaks: `next_quote_number` derives the next sequence from the newest quote row BY ID.
  Both revise flows poison it. API revise (app/routers/crm/quotes.py:53-71) renames the old row
  to `-R1` and inserts a new highest-id row keeping the base number → next number computed is
  already taken → IntegrityError on `uq_quotes_quote_number` (migration 174). Workspace revise
  (app/routers/htmx/quotes.py:591) numbers the new row `...-R2` → `split("-")[-1]` ValueError →
  seq=1 → `Q-2026-0001`, which always exists.
- Blast: every subsequent quote creation 500s (builder assemble, req quote, proactive convert)
  until year rollover or manual data surgery. The 3-retry loop in crm/quotes.py:247-275
  recomputes the identical colliding number (its test passes only because it mocks the
  generator). Verified by executing the real code against the real model.
- Fix: dedicated per-year sequence table with atomic UPSERT...RETURNING (or SQL MAX over a
  strict `Q-YYYY-NNNN` regexp). Never derive from newest-by-id; never fall back to seq=1.
  Also the `with_for_update()` cannot serialize first-of-year concurrent creates.

**2. Deleting a quote in the workspace CASCADE-deletes the buy plan tree, incl. PAID prepayments**
- Where: app/routers/htmx/quotes.py:148-164 (delete at :160-161)
- What breaks: the HTMX DELETE checks only status==DRAFT. The reopen endpoint (htmx/quotes.py:
  167-185) legally returns SENT/WON/LOST quotes to DRAFT with no buy-plan check. Buy plans are
  built from SENT/WON quotes (buyplan_builder.py:78). `buy_plans_v3.quote_id` is
  ondelete=CASCADE (models/buy_plan.py:82, migration 020), cascading to BuyPlanLine (:201),
  QualityPlan (quality_plan.py:55), and Prepayment (quality_plan.py:170) — including rows with
  status PAID and wire references. No listener, RESTRICT constraint, or audit intervenes.
- Contrast: the JSON sibling has the guard (crm/quotes.py:373-375) — the HTMX path skips it.
- Fix: same linked-buy-plan 400/409 check in `delete_quote_htmx` via one shared service both
  delete endpoints call.

**3. Prepayment wire notices marked delivered when Graph rejected the send**
- Where: app/services/prepayment_notifications.py:530-541
- What breaks: `_send_group_email` discards `gc.post_json`'s return and sets `sent_any=True`
  unconditionally; only raised exceptions mark failure, but the Graph client returns error
  dicts on 401/403/400 and exhausted retries without raising. A VOIDED "DO NOT WIRE — claw
  back" notice (or an OK-TO-WIRE) is recorded email_sent=True, and the honesty alert at :277
  is suppressed exactly when both channels failed. Accounting can wire against a voided
  prepayment while AVAIL records the stand-down as delivered.
- Fix: treat `result.get("error")` as a failed send per recipient, matching the pattern the
  codebase already uses at app/routers/htmx/offers/follow_ups.py:163-172 and
  app/services/quote_send.py:133.

### HIGH

**4. Unchecked Graph error-dict family — five more sites falsify send/lookup status**
Root cause shared with #3: graph_client returns error dicts (graph_client.py:278, 304, 318).
One fix pattern (check/raise on `result.get("error")`) clears all of these:
- a) app/services/approvals/notifications.py:52 — approval outbox marks rows `sent_at` on
  4xx/exhausted-retry failures; the docstring's re-raise contract is false; retry/dead-letter
  (approval_outbox.py:119-120) never engages; decision notifications permanently lost.
- b) app/email_service.py:498 — `_find_sent_message` treats error dicts as clean empty Sent
  scans and returns the resend-authorizing None; resell Retry
  (resell_outreach_service.py:991, 1033-1043) then re-sends an email that already delivered —
  deterministic double-send per click under Graph throttling or missing Mail.Read.
- c) app/routers/htmx/offers/replies.py:305-312 — vendor reply marked REVIEWED and "sent" on a
  rejected send; response drops out of the needs-action queue; deal silently stalls.
- d) app/services/proactive_service.py:470-490 and :720-733, plus proactive_digest.py:321-334 —
  proactive offers/digests flipped to SENT (matches SENT, throttles written, overlapping
  drafts deleted) on a rejected send; customer never contacted, opportunity lost.
- e) app/services/prepayment_notifications.py:267-269 — `post_teams_channel_card` never raises
  (teams_notifications.py:82-85), so `teams_sent=True` always; the both-channels-failed
  honesty alert at :277 is unreachable whenever a Teams webhook is configured. Its covering
  test passes only by mocking a behavior the real function cannot exhibit.

**5. Failed proactive send still records a phantom "sent" offer and shows a success banner**
- Where: app/services/proactive_service.py:486-534; models/intelligence.py:402-403;
  app/routers/htmx/proactive.py:508-540
- What breaks: `send_proactive_offer` creates the ProactiveOffer with no explicit status, so
  model defaults `status='sent'`, `sent_at=now` apply; `db.commit()` at :533 persists it on
  BOTH success and failure and the router treats any non-exception return as "Offer sent to N
  contact(s)". Verification correction: with an expired token the router passes "no-token"
  (:527) and Graph's 401 comes back as an error dict — the code takes the SUCCESS branch
  (matches SENT, throttles written), which is worse than the claimed except-path; the
  except/FAILED path is separately reachable via transport failures. FAILED matches are read
  nowhere (lists query status NEW only) so the demand vanishes; phantoms inflate the
  scorecard and are later "expired" as real sends.
- Fix: create as DRAFT, flip to SENT only after a verified-successful send, surface failure to
  the router; 400 on missing token like the prepared-send endpoint already does.

**6. Stored XSS: attachments served inline with attacker-controlled Content-Type**
- Where: app/services/attachment_service.py:56-58, 211, 304-308
- What breaks: validation is extension-only (bytes never sniffed; ".txt" allowed), the
  multipart part's client-set Content-Type is stored verbatim, and `open_attachment` streams
  it inline on the app origin. CSP allows 'unsafe-inline' (main.py:614). A "poc.txt" with
  Content-Type text/html executes script in any viewer's authenticated session.
- Precondition: fires when the company-library backend is configured
  (settings.datasheet_library_drive_id — the intended prod backend; currently defaults "").
- Fix: fixed extension→MIME allowlist or magic-byte sniff (avatars.py:124-127 already does
  this); serve `Content-Disposition: attachment`; reject sniffed html/svg/xml.

**7. Alpine expression-injection XSS from external search-result vendor names**
- Where: app/templates/htmx/partials/search/vendor_card.html:28-29
- What breaks: `vendor_name`/`mpn_matched`/`source_type` are interpolated raw into
  single-quoted JS strings inside Alpine `:checked`/`@change` directives. The browser decodes
  Jinja's HTML entities before Alpine evals the attribute as JS (CSP has 'unsafe-eval' for
  Alpine, main.py:604-620), so a crafted listing name from live feeds (BrokerBin/eBay/
  OEMSecrets/LLM-extracted) executes JS on render, no interaction needed. Even benign
  apostrophes ("Fry's") kill the row's shortlist checkbox.
- Fix: emit values via `|tojson` into x-data/data-* and read them in the handler; never build
  Alpine expressions from raw external strings.

**8. Quote-builder revise hijacks arbitrary quotes and collapses combined quotes**
- Where: app/services/quote_builder_service.py:522-528; routers/quote_builder.py:459-464
- What breaks: `payload.quote_id` is loaded via raw `db.get` — no ownership check, no check

  the hidden quote_id and takes over another rep's quote number under a different customer.
  The htmx revise path has exactly the missing guards (get_quote_for_user + full membership,
  htmx/quotes.py:586-634).
- Fix: resolve via get_quote_for_user semantics, require requisition membership to intersect
  req_ids, and carry `requisition_ids_for_quote` into the revision.

**9. Approval reassign hands money-gate authority to ineligible users**
- Where: app/services/approvals/events.py:136-141; routers/approvals.py:156-158

**10. Prepayment decided via the engine JSON endpoint is permanently stranded**

**11. Resumed buy plans can never complete; PENDING-halt resume bypasses approval**
